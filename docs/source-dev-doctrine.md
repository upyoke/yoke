# Source-dev doctrine — working on Yoke itself

The repo rules file carries the short normative form of each rule here.
This is the deep home it points at: the same rules with the reasoning,
the release-train shape, the flag matrices, and the incidents that
produced them. Repo-internal — it is not part of the install bundle,
because none of it is true of a project that merely uses Yoke.

## CLA signatures branch — Hard Rule
- **`origin/cla-signatures` is permanent governance state, not a leftover lane.** The CLA Assistant workflow appends signatures there and the required `signature-check` status reads them. Never delete, force-push, reset, or prune it during cleanup — divergence from `main` with no merge-base is expected — and leave it unprotected so the workflow can write.

## Repo file layout

Repo-relative paths:
- API: engine source is `packages/yoke-core/src/yoke_core/` (`yoke_core.cli.db_router`, `yoke_core.api.service_client`, `yoke_core.engines.*`, internal test runner, API server), and `runtime/api/` is `yoke_core`'s second declared root where the root IS the package — its tests, fixtures, helpers, and in-tree tools, importable as `runtime.api.*` too. An importable name never implies a directory at the repo root: `yoke_harness` splits the same way across `packages/yoke-harness/src/` and `runtime/harness/`, so resolve any module through the complete `package_roots` mapping your DB packet renders from `architecture_model` rather than guessing from the name. Agent recipes via `yoke <subcommand>` unless a packet marks a retained tool shape.
- Skills: `.agents/skills/yoke/{command}/SKILL.md` (`.claude/skills/yoke/` compat symlink). Agents: `runtime/agents/{agent}.md`; Claude adapters `runtime/harness/claude/agents/yoke-*.md` via `yoke agents render`; `.claude/agents` symlinks there. Prompt philosophy: `docs/prompt-philosophy.md`. Backlog: `yoke items get YOK-N body` (virtual; no generated `.md` bodies).
- Browser: packaged under `packages/yoke-harness/src/yoke_harness/browser_runtime/`, materialized to `~/.yoke/browser-runtime/` (`yoke_harness.browser_*` / `yoke_core.domain.browser_*`). Harness adapters: `runtime/harness/{harness-id}/`; Codex via `.codex/hooks.json` and `codex app <repo>`.
- Machine config `~/.yoke/config.json`; the machine id it carries is registered in the control-plane `machines` row that every relay poll, launch, plan-limit and surface-policy row names, and whose `access` document decides which actors may spend that machine's capacity (`yoke machine list|show|register|settings`, [`docs/machine-registry.md`](machine-registry.md)); project surfaces `.yoke/`; docs `docs/`; design specs in `items.design_spec`. Hook sources: `runtime/harness/claude/settings.json` materialized at `.claude/settings.json`, plus `runtime/harness/codex/hooks.json` through the `.codex` link.

## Source-dev doctrine

- The generic runner is the source-dev `uv run --frozen python3 -m yoke_core.tools.run_tests` helper; use project-provided commands or the retained watcher wrappers when they are named in your packet. `uv run --frozen` makes a clean worktree use its locked development dependencies and its own source packages without requiring an activated virtualenv. Run `yoke dev ruff-changed --base <ref>` for changed-path lint; add `--format-check` to verify formatting; detailed recipes: [`docs/testing-verification.md`](testing-verification.md).
- The local verification default for Yoke code is the impacted selection: `yoke watch pytest --impacted main --bounded` (reverse-import + string-reference reachability over the branch diff, plus an always-run contract-test floor; `--impacted` reports an unbounded verdict instead of widening; `--bounded` is a no-op and `--widen` takes the local full sweep). **That selection executes on CI, not on this machine.** Yoke declares a `ci_workflow_file` capability, so `yoke watch pytest` and the generic runner behind it push the lane commit, dispatch `.github/workflows/yoke-tests-selection.yml` against it with the merge base the change is measured against, and adopt that run's conclusion as the verdict — the workstation serves sessions while CI runs tests. `--local` (or `YOKE_PYTEST_LOCAL=1` for a whole shell) is only a small targeted check expected to finish in about one minute, and every local run takes its xdist workers from one machine-wide budget. A remote run refuses an uncommitted tree and a checkout on the base branch (commit, then run on CI — uncommitted work does not justify `--local`), and drops `-n`/`--numprocesses`/`--rootdir`, which describe this machine. The full three-anchor sweep `yoke watch pytest -- runtime/api/ runtime/harness/ tests/` is CI's job on every pull request and push to main; run it locally only as the CI-outage fallback or for narrow debugging. Both shapes inject xdist `-n auto` unless `-n` is passed. Use `-- -n 0` for sequential order-sensitive debugging. A CI failure on a test the impacted run skipped is a selector defect — see [`docs/testing-verification/full-suite-authority.md`](testing-verification/full-suite-authority.md) for the triage, the widening telemetry, and the one-full-execution contract. Yoke's project-default Command case runs this same impacted selection, so per `## Testing` above the gate run is the last local execution.
- Harness coverage is Python-owned under files such as `runtime/harness/test_hook_runner_runner.py`, `runtime/harness/test_hook_runner_telemetry.py`, `runtime/api/test_service_client.py`, and `runtime/api/test_sessions.py`. Never set `YOKE_DRY_RUN=1` in tests; the suites mock their own GitHub side effects.
- **Hosted release flows are project-local; Platform owns promotion.** The active Yoke hosted routes are `yoke-hosted-stage-consumer-bound` (stage), `yoke-hosted-production-release-qa` (the normal production release), and `yoke-hosted-production-hotfix-consumer-bound` (production hotfix); the earlier `-typed-target`, `-warm-gated`, `-no-ci-gate`, and `yoke-hosted-production` definitions are disabled history, because a definition a run has referenced is immutable — changing a route retires the prior definition and adds the next one. The Yoke bridge allocates the annotated release tag, waits for the wheel and server-image factories, and dispatches Platform's single promotion boundary. Each promotion publishes the release only to its target environment's distribution index, so a wheel is resolvable only for an environment whose flow has run. It passes the registered `stage` or `prod` environment name resolved from the run's typed environment reference (the `{target_environment}` stage-input placeholder) unchanged through the Platform boundary. Each route closes with a `warm-up` stage that pays the rolled box's cold start before the run reports success, so the first heavy relayed call after a release is not the operator's. Platform items use `platform-stage-hosted`, `platform-prod-independent-hosted`, or `platform-prod-hotfix-hosted` and dispatch the Platform train directly. Do not hand-create release tags, hand-edit `yoke-release-pin.txt`, or dispatch component deploy workflows as the normal path. **One Yoke release deploys both repos.** Every hosted route's `hosted-release` stage binds `consumer_sha` to Platform `main`'s tip as the run starts, and the bridge hands that exact commit to Platform's `yoke-release-promote.yml` as `proven_consumer_sha` — so a Yoke release ships Platform at whatever `main` pointed at when the run resolved the binding, and a Platform change merged before that moment is already live once the run succeeds. **Membership follows that code:** the run records the Platform commit it resolved, and start-time enrollment admits the delivery-ready PLAT items that commit carries as ordinary members — membership row, requirement snapshot, item-scoped QA wake, close-out — so a Platform item the Yoke release shipped is closed by the run that shipped it. No Platform-only run is needed to record a delivery that already happened. Still check the ordering: Platform work merged after the run resolved the binding is not in the recorded commit, did not ride, and genuinely needs its own run. Desired pin authority is `environments.settings.release.yoke_pin` on Platform's `yoke-api-stage` / `yoke-api-prod`; environment branches materialize the pin for builds. Promotion restores that materialization when deploy fails and records the desired pin only after success — verify with `yoke release-pin verify`. A Platform ref captured before a pin bump can still roll the engine backward; re-read the pin branch (or desired pin) after any Yoke release before starting a Platform run. **A release is not published until the hosted host has been built against it.** Each hosted-release stage declares an `input_bindings` map (`consumer_sha` bound from Platform `main`), resolved exactly once when the run starts — via a plain `git ls-remote` against Platform's registered checkout, or that project's authorized repository binding on a host holding no checkout, never a not-yet-served field of the release it is gating — and recorded on the run in `deployment_runs.bound_sources`. Every stage dispatch, and every later delivery question, reads that recorded commit, so a retry cannot drift and the release can say exactly which Platform revision it shipped. Before the bridge allocates the annotated tag — the first irreversible act — `runtime/api/tools/require_platform_consumer_compatibility.py` takes that exact `--consumer-sha` and dispatches Platform's existing required `platform-release-pin-check.yml` with `product_ref` set to the exact release commit, which redirects that check's build onto the candidate source instead of the pinned wheel, and adopts its conclusion — refusing when proof is missing, failed, or names no revision it proved. It then hands promotion the consumer revision it read, so promotion refuses to ship against a different one. Platform's promotion-time check stays the final backstop. The same pair is advised earlier, inside `yoke-ci.yml`'s independent `consumer_advisory` job (a `./.github/workflows/consumer-compatibility-advisory.yml` reusable-workflow call, `needs`-free so repo-contracts and the shard matrix never wait on it): `runtime/api/tools/consumer_compatibility_advisory.py` uses the same one changed-path scope and, having no durable driver authority of its own, dispatches onto Platform's trunk branch by name and trusts the run's own report rather than demanding an exact match; when the change touches the host-consumed surface it reports checked / not applicable / not checked. It never decides yoke-ci's own required checks — the called job's own continue-on-error covers any failure there, setup steps included, since a job calling a reusable workflow cannot carry that key itself — the scoped credential is passed explicitly by name (an optional `workflow_call` secret, never `secrets: inherit`) and bound to that single step, and a fork run — which never receives one — says the pair was not checked rather than implying a clean answer. Why: [`docs/archive/decisions/consumer-compatibility-before-contract-delivery.md`](archive/decisions/consumer-compatibility-before-contract-delivery.md).
- **Control-plane connection authority.** HTTPS `prod` is the normal product/API authority: registered `yoke` commands relay there; it has no local database to open for raw SQL writes. `prod-db-admin` is the paired local-Postgres connection to the same universe — direct database authority for sanctioned source-dev/admin work and audited break-glass SQL (`yoke db` `--help` names the query path under `--env prod-db-admin`). Deploy, rehearse, and release command-shaped surfaces also require that admin connection here, because every Yoke release replaces the very API serving this control plane — that is this repo's own shape, not what an ordinary project does, and those projects deploy over their configured HTTPS connection. Neither Yoke nor Platform deploys from a branch push; the private Platform deploy runbook is the detailed operator reference for this installation's cross-repository release train.
- **Fleet migration preflight — Yoke's adapter.** Run `yoke watch preflight -- <environment-or-admin> [db ...] [--record-receipt ...]` (`--help` for the complete usage) for the Yoke-project binding the governed-migration contract requires: it converges a throwaway copy of every tenant database on a connected cluster through the real boot sequence, reads the live databases and nothing more, streams through the sentinel-aware unbuffered watcher, and exits with the preflight's status. The fleet is narrower than every Yoke-schema database on the cluster — the Platform catalog, abandoned scratch databases, and the validation database rehearsal applies history into and leaves behind are each owned by something other than a tenant — so the run rosters every candidate before copying any of them, naming member or not and why; read that roster rather than assuming the fleet. The positional may be the registered environment (`stage`) or its paired admin connection (`stage-db-admin`); `--engine-wheel` is optional. `--record-receipt` writes the receipt the hosted release gate reads for the environment whose fleet the positional named (one environment's receipt never satisfies another; `--receipt-env` names the control plane that records it, not the fleet; the receipt states whether it rehearsed the source tree or a wheel). The receipt is durable state, not telemetry: it lands on that environment's own `environments.settings` document under `release.fleet_rehearsal`, one leaf per covered history entry and one per covered schema-shape digest, each naming the rehearsal run whose identity sits beside them — so coverage cannot expire, and coverage read for one environment can only ever have been written for that environment. Both release gates read it through the registered `projects.environment_settings.get` projection, which authorizes on the project read, so a deploy identity that lacks that permission is told it cannot check rather than told the build is unrehearsed. Why each rule exists: [`docs/archive/decisions/workflow-definitions-are-universe-data.md`](archive/decisions/workflow-definitions-are-universe-data.md) (canonical-serializer drift caused a fleet-wide boot refusal), [`docs/archive/decisions/fleet-preflight-release-gate.md`](archive/decisions/fleet-preflight-release-gate.md) (why the release gate stops the release instead of the fleet), [`docs/archive/decisions/ordered-cumulative-migrations.md`](archive/decisions/ordered-cumulative-migrations.md) (the stage-fleet outage both gaps caused together).
- **Substrate names — read the packet, don't restate.** The `harness_id` enum, the function-call dispatch entrypoint, and the request/response models are rendered by the `main_agent` (and `*_agent`) packets at session start; read them there. Regenerate via `agents.render.run`; check drift via `agents.render.check`.
- **Same-PR packet teaching on Yoke-surface gap failures.** When an agent in a Yoke `/yoke` work item hits a `no such column`, `cannot import name`, or `unexpected keyword argument` failure against a Yoke-owned surface (any `runtime.api.*`, `runtime.harness.*`, or a Yoke DB table / column / Python helper), the SAME PR that observes the failure ships the matching packet teaching: name the real surface in the relevant `schema_api_context_tables_*.py` entry AND add a `notes` clause that names the wrong guess the agent made. The seed catches the gap; the packet rendering surfaces the canonical name to the next agent.
- **Layer-explicit packet names.** Every LLM-facing packet role uses an `*_agent` suffix: `main_agent` (top-level session) plus the five Bash-capable subagents `architect_agent`/`engineer_agent`/`tester_agent`/`simulator_agent`/`boss_agent`. The substrate manifest contract (hooks, identity, cwd binding, render format, supported commands, parity limits) is documented separately as `harness_contract` in [`docs/harness-bootstrap.md`](harness-bootstrap.md) + [`runtime/harness/manifest-schema.md`](../runtime/harness/manifest-schema.md) — deliberately NOT a `schema_api_context` role.
- **Tier-discipline doctrine.** The seven teaching tiers and their backstop HCs (`HC-tier-schema-bleed`, `-tier-cli-shape-bleed`, `-packet-tier-completeness`, `-progressive-disclosure-direction`, `-tier-module-path-resolution`) are documented at [`docs/archive/decisions/teaching-tier-discipline-audit.md`](archive/decisions/teaching-tier-discipline-audit.md).
- **Subagent DB context:** Bash-capable agent prompts (architect/engineer/tester/simulator/boss) carry generated `<!-- YOKE:DB-PACKET role=<role>_agent topic=T … -->` marker pairs the renderer fills with role/topic-scoped schema/API content from `schema_api_context`; the top-level session gets the compact `core`+`claims` spine via `main_agent_packet`. Subagents inherit the packet through the rendered prompt — never hand-copy a stale schema cheat sheet. **The packet is the authoritative schema surface** — consult it (or `information_schema` via `yoke db read` / a direct Read of the schema module) before answering any schema question; don't infer columns/tables from work item or skill prose. Regenerate after schema changes via `agents.render.run`; detect drift via `agents.render.check`. Canonical claim-holder lookup: `python3 -m yoke_core.hooks.sessions_cli who-claims <item-id>` — in-tree, not importable from an installed Yoke; add `--current-episode` to bound the output to the current episode, tagging each claim `episode_scope=current_episode|inherited_from_prior_episode|unknown` plus an `episode_boundary=<ts|none>` line (the portable, episode-blind read is `yoke claims work holder-get PREFIX-N`). Typed work-claim targets use `target_kind` plus one canonical JSON object in the `scope` column (`item={"item_id":N}`, `epic_task={"epic_id":N,"task_num":N}`, `process={"process_key":K,"conflict_group":G}`, `steering={"project_id":N}`), each validated against exactly its own keys; there is no specialized target column, and the packet's `work_claims` stanza carries the live kind list. The drift gate refuses known-stale owner/claim/session guesses.
- **Bash-capable ⇒ packet-capable.** Granting Bash to an agent requires a `*_agent` packet role in `seed.ROLE_TOPICS` + marker pairs in its prompt. Product Manager and Product Designer stay non-Bash by design (tools: `Read, Grep, Glob`; orchestrators pass them context via dispatch prompts) — if they ever gain Bash, they gain packet roles in the same slice. Canonical bodies may carry harness-conditional blocks `<!-- YOKE:HARNESS <id> … -->`; the renderer (`agents_render_conditional`) keeps the matching harness id and elides the rest (known ids `claude`/`codex` from one constant; nested/orphan/unknown surface via `HC-harness-substrate-drift`). Use these to fence primitives a harness does not declare (`Monitor`, `Bash(run_in_background)`, `ScheduleWakeup`, `TaskOutput`, `TaskStop`, `PreToolUse`) so the wrong-harness adapter never inherits them — check `agent_wake` in the target manifest rather than assuming a wake primitive is Claude-only.
- **Workspace-anchored writers.** Repo-tree writers (renderers/generators landing tracked files under `runtime/` or `docs/`) MUST take an explicit `target_root: Path` kwarg; resolving the target from ambient cwd (`git rev-parse`, `Path.cwd()`, bare relative consts) in the hot path is forbidden. Only the CLI resolves `target_root` (`--target-root`/`$YOKE_RENDER_TARGET_ROOT`, else repo-root helper when no anchor and not in a worktree). Primary guard: `workspace_authority.assert_target_under_session_work_authority(target)` — reads the session's live `work_claims`, refuses targets outside the claimed worktree/allowlist (replaced the stale `$YOKE_BOUND_WORKSPACE` snapshot). Tracked-source writers call it before writing; `HC-workspace-anchored-writer-authority` enforces against the canonical `IN_SCOPE_WRITERS` list (`.yoke/doctor/check_workspace_anchored_writer_authority.py`) — add new writers there. Untracked generated-view writers (e.g. `rebuild_board.rebuild_one`, which renders project-local `.yoke/BOARD.md` on explicit request) are out of scope (refusing them would break `yoke board rebuild`) but still call `assert_seed_source_under_target_root(...)` to catch a seed/schema module loaded from a different checkout than `target_root`. Legacy cwd check: lint `lint_workspace_cwd_match.py`.
- **Session identity resolution:** ambient session id resolves automatically — `$YOKE_SESSION_ID` first, then the channels belonging to the harness family this process actually runs under: that family's own session env vars, the hook-written process-anchor registry, and for Cursor the hook-written conversation mapping (`session_ambient_identity`). The owning family is the nearest harness ancestor in the process tree, because every harness session env var is inherited by whatever that harness starts — so a harness launched from inside another harness's shell resolves to its own session, or to nothing when its own channel is out of reach, never to its launcher's. The anchor walk stops at a harness process that hosts many conversations under one pid, on the read side as well as the write side: an anchor above such a host names a *different* session, and resolving through it would act with that session's authority. A harness that neither stamps the env chain nor can be anchored identifies through the conversation mapping instead; never export session env vars to self-bootstrap (`actor_session_missing` inside a harness = infrastructure bug, report it; from a plain terminal the same refusal names the harness-session path instead, and the operations a person runs before any session exists are session-optional by declaration — `terminal_reachable_functions`). Actor id = `harness_sessions.actor_id` keyed by `session_id`, and authority follows the person: a session a person opened binds that person, while a session another session LAUNCHED binds the launching actor transitively (the launch's `requester_actor_id`, read at registration through the authenticated launch side channel, outranks both the machine's OS login and a relay's bearer token; an unreadable launch refuses registration rather than falling back to either). Every action one session takes on another — message, wake, keep-alive, terminate, launch — writes a `SessionActionPerformed` row into the TARGET session's history carrying the ACTING actor (`yoke events query --session <target> --event-name SessionActionPerformed`), and is role-checked against the target's project by `session_action_authority`: project membership to message, wake, hold alive, or terminate a launched worker; project owner or org admin to terminate another actor's interactive session, with refusals naming the actor, the roles it holds, and the action (`docs/archive/decisions/session-actor-follows-the-person.md`). No `get_active_session_id` exists — pass `{"session_id": ...}` alone; dispatcher fills actor_id server-side; `--session-id` = operator-debug override. Scripts importing `runtime.*` live in-tree (`runtime/api/tools/<name>.py`), never `/tmp`; or `pip install -e .` once (`lint_python_runtime_import_in_tmp.py`). JSON behind `yoke_core.domain.json_helper`; YAML behind `yoke_core.domain.yaml_helper`.
- **Worktree-dev (editing Yoke itself):** the installed `yoke` and bare `python3 -m ...` resolve main's editable install, never a claimed lane. Run direct lane-source commands through `yoke dev run -- <command>`; it derives every source root from the claimed checkout, runs there regardless of caller cwd, reports all Yoke package and `runtime` import origins, and refuses partial or outside-tree resolution. A nested `yoke <subcommand>` binds too: dev run executes the CLI on the interpreter whose origins it just reported rather than handing the command to the installed launcher, which would resolve its own checkout — so `yoke dev run -- yoke watch qa-case -- --requirement-id N` verifies lane code. The `watch_pytest`/`run_tests` wrappers already self-bind through the same `yoke_core.tools._source_pythonpath` resolver. Yoke control-plane authority is Postgres; use registered `yoke <subcommand>` surfaces for state access, and treat the retired `worktree paths db` mode as a refusal guard rather than a connection recipe.
