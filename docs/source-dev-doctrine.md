# Source-dev doctrine — working on Yoke itself

The repo rules file carries the short normative form of each rule here.
This is the deep home it points at: the same rules with the reasoning,
the release-train shape, the flag matrices, and the incidents that
produced them. Repo-internal — it is not part of the install bundle,
because none of it is true of a project that merely uses Yoke.

## Worktree cleanup

- **Lane and deploy-run worktree retirement is one contract:** what makes a
  directory disposable, why a project must declare its rendered gitignored
  views, how a self-deploy run's detached driver tree is retired from its run
  status, and what the `max_active_worktrees` refusal tells you to do about
  each kind. [`docs/source-dev-worktree-cleanup.md`](source-dev-worktree-cleanup.md).

## CLA signatures branch — Hard Rule
- **`origin/cla-signatures` is permanent governance state, not a leftover lane.** Both CLA workflow jobs run only in `upyoke/yoke`; forks and other copies skip upstream's CLA. The CLA Assistant workflow appends signatures there and the required `signature-check` status reads them. Never delete, force-push, reset, or prune it during cleanup — divergence from `main` with no merge-base is expected — and leave it unprotected so the workflow can write.

## Serving catalog regeneration

After changing schema declarations, regenerate the serving catalog from the
complete source initialization chain in a disposable local test database:

```text
yoke dev run -- python3 -m runtime.api.tools.schema_catalog_render --target-root <claimed-checkout>
```

The tool checks every classified instant is native, excludes derived views,
and writes only the explicit checkout's generated catalog declaration. It
never reads or changes a live universe. Re-run the born-universe serving check
and commit the regenerated source alongside the schema change.

## Product code never branches on a project name

Product code runs for every install, so it reads the declared fact a project
name would stand in for: a capability or environment setting, the
installation's self project, or a property of the checkout.
`HC-project-name-literal` scans for the registered project names in
comparisons, project keywords, constants, dict entries, project-named calls
and returns, SQL parameters, and SQL slug tests. A legitimate remaining site
carries a named allowance in
`yoke_core.domain.lint_project_name_literal_allowances`; a site whose
replacement is in flight is listed as pending and reported as WARN; an
allowance that no longer matches fails the check.

## Source-dev doctrine

### Direct database authority for source development and operators

Discover configured connections with `yoke env list`. HTTPS `prod` owns normal
registered operations. The paired `prod-db-admin` connection administers that
same control plane directly; every real durable record stays on prod, including
stage-targeted release and rehearsal receipts. Stage is disposable test state.

When a sanctioned operator mutation has no registered command, the audited
source-dev query path is
`yoke --env prod-db-admin dev run -- python3 -m yoke_core.cli.db_router query "SQL"`.
Governed schema/data changes still require their
migration history and rehearsal; this query path does not replace that contract.
For a function the serving API predates, use an existing served command or the
paired authority only when the operator already holds this control plane.

Only source-dev/admin setup creates these machine-local profiles:

```text
yoke dev db-admin setup prod --control-plane-env prod --yes
yoke dev db-admin setup stage --project P --database MODEL --yes
yoke dev db-admin exec P-stage-MODEL-db-admin --dsn-var APP_DSN -- <command>
```

Control-plane setup reads `current_database()` through the exact named HTTPS
connection's tenant route; deploy environment settings supply stack, region,
endpoint, and secret ARN, not the tenant database identity. Project database
setup instead reads the `migration_model` declaration's `authoritative_db`
(`database_name`, `endpoint_output`, `secret_arn_output`) and the environment's
stack, bastion, and region. Profiles store only the managed secret ARN. `exec`
resolves that secret through the project's `aws-admin` capability, opens the SSH
forward, and passes the DSN to one subprocess. Never print, log, or store the DSN;
named refusals identify the missing profile, capability, secret, or connection
and its recovery. Product setup does not create these operator profiles.

Rehearse Yoke migrations from the claimed lane through the paired authority:

```text
yoke --env prod-db-admin dev run -- yoke migration rehearse PREFIX-N
```

The item and durable lease/audit receipts live on prod. Migration code runs only
against the separately bound disposable validation database, whose live cluster
and database identity must differ from the authority. Preserve each
environment's fleet-preflight receipt and the rehearsal's
`LIVE_DB_MIGRATION:<model>` hold, which the item's merge landing releases.
Yoke self-deploys use the same paired authority because they replace the API
that otherwise serves run state. Follow the release-pair rule below and the
steering skill's source-dev delivery guide; ordinary projects deliver over HTTPS.

Tenant-fleet content-identity adoption is also an attested operator operation:

```text
python3 -m yoke_core.tools.adopt_migration_content_identity stage-db-admin \
  --wheel <attested-yoke-core-wheel> \
  --manifest <attested-migration-history.json> \
  --release-evidence <attested-migration-history-record.json> \
  --repository owner/example-project --source-commit <full-commit> \
  --manifest-sha256 <sha256> --adopted-by operator:<name> --prepare
```

Select the fleet's configured admin environment, then authenticate the exact
wheel, manifest, and release record before opening any database. Missing or
mismatched attestation refuses; retain the secret-free identity receipt.
Evidence writes from admin connections relay to their configured HTTPS evidence
plane so hosted reviewers can open captures. GitHub status and local merge
authorization likewise prove through that paired HTTPS plane.

### Source execution and release rules

- **Actor-state bootstrap during a self-deploy.** The paired `prod-db-admin` connection creates and drives a production run against the existing database before the new server boots and converges additive columns. An actor row without `status` therefore has legacy active authority; once the column exists, only an explicit `active` value has authority. Keep authorization, approver, notification-audience, and roster reads compatible across that boundary. Actor enable/disable itself refuses until boot convergence. Do not apply the column manually. A correction merged while an earlier Stage run is executing needs a new Stage/Production pair pinned to the corrected candidate; the old Stage receipt does not prove the new build.
- **Environment behavior is declared, never inferred from the name.** Endpoints, QA execution gating, release membership, the paired admin connection, the warm-up serving connection, observability, and the production role live on that environment's settings document (`yoke projects environment-settings`). A missing declaration is a named refusal, not an empty mapping and not production behavior borrowed from a conventional name.
- The generic runner is the source-dev `uv run --frozen python3 -m yoke_core.tools.run_tests` helper; use project-provided commands or the retained watcher wrappers when they are named in your packet. `uv run --frozen` makes a clean worktree use its locked development dependencies and its own source packages without requiring an activated virtualenv. Run `yoke dev ruff-changed --base <ref>` for changed-path lint; add `--fix-format` to write the formatting CI checks, or `--format-check` to only report it. `yoke dev import-check <module> ...` imports named modules from the lane and names the file that answered each one, which is the sanctioned shape for smoke-testing source you are editing. Detailed recipes: [`docs/testing-verification.md`](testing-verification.md).
- The local verification default for Yoke code is the impacted selection: `yoke watch pytest --impacted main --bounded` (reverse-import + string-reference reachability over the branch diff, plus conftest fixture-use and function-registry dispatch edges and an always-run contract-test floor; `--impacted` reports an unbounded verdict instead of widening; `--bounded` is a no-op and `--widen` takes the local full sweep). **That selection executes on CI, not on this machine.** Yoke declares a `ci_workflow_file` capability, so `yoke watch pytest` and the generic runner behind it push the lane commit, dispatch `.github/workflows/yoke-tests-selection.yml` against it with the merge base the change is measured against, and adopt that run's conclusion as the verdict — the workstation serves sessions while CI runs tests. `--local` (or `YOKE_PYTEST_LOCAL=1` for a whole shell) is only a small targeted check expected to finish in about one minute, and every local run takes its xdist workers from one machine-wide budget. A remote run refuses an uncommitted tree and a checkout on the base branch (commit, then run on CI — uncommitted work does not justify `--local`), and drops `-n`/`--numprocesses`/`--rootdir`, which describe this machine. The full three-anchor sweep `yoke watch pytest -- runtime/api/ runtime/harness/ tests/` is CI's job on every pull request and push to main; run it locally only as the CI-outage fallback or for narrow debugging. Both shapes inject xdist `-n auto` unless `-n` is passed. Use `-- -n 0` for sequential order-sensitive debugging. A CI failure on a test the impacted run skipped is a selector defect — see [`docs/testing-verification/full-suite-authority.md`](testing-verification/full-suite-authority.md) for the triage, the widening telemetry, and the one-full-execution contract. Yoke's project-default Command case runs this same impacted selection, so per `## Testing` above the gate run is the last local execution.
- Harness coverage is Python-owned under files such as `runtime/harness/test_hook_runner_runner.py`, `runtime/harness/test_hook_runner_telemetry.py`, `runtime/api/test_service_client.py`, and `runtime/api/test_sessions.py`. Never set `YOKE_DRY_RUN=1` in tests; the suites mock their own GitHub side effects.
- **Hosted release flows are project-local; Platform owns promotion.** The bridge workflow runs only in `upyoke/yoke`; forks and other copies skip upstream hosted delivery. The active Yoke hosted routes are `yoke-hosted-stage-release-qa` (stage, after its engine revision is installed), `yoke-hosted-production-release-qa` (the normal production release), and `yoke-hosted-production-hotfix-consumer-bound` (production hotfix); the earlier `-typed-target`, `-warm-gated`, `-no-ci-gate`, and `yoke-hosted-production` definitions are disabled history, because a definition a run has referenced is immutable — changing a route retires the prior definition and adds the next one. The Yoke bridge allocates the annotated release tag, waits for the wheel and server-image factories, and dispatches Platform's single promotion boundary. Each promotion publishes the release only to its target environment's distribution index, so a wheel is resolvable only for an environment whose flow has run. It passes the registered `stage` or `prod` environment name resolved from the run's typed environment reference (the `{target_environment}` stage-input placeholder) unchanged through the Platform boundary. Each route uses a `warm-up` stage that pays the rolled box's cold start before the run reports success, so the first heavy relayed call after a release is not the operator's. Platform items use `platform-stage-hosted`, `platform-prod-independent-hosted`, or `platform-prod-hotfix-hosted` and dispatch the Platform train directly. Do not hand-create release tags, hand-edit `yoke-release-pin.txt`, or dispatch component deploy workflows as the normal path. **One Yoke release deploys both repos.** Every hosted route's `hosted-release` stage binds `consumer_sha` to Platform `main`'s tip as the run starts, and the bridge hands that exact commit to Platform's `yoke-release-promote.yml` as `proven_consumer_sha` — so a Yoke release ships Platform at whatever `main` pointed at when the run resolved the binding, and a Platform change merged before that moment is already live once the run succeeds. **Membership follows that code:** the run records the Platform commit it resolved, and start-time enrollment admits the delivery-ready PLAT items that commit carries as ordinary members — membership row, requirement snapshot, item-scoped QA wake, close-out — so a Platform item the Yoke release shipped is closed by the run that shipped it. No Platform-only run is needed to record a delivery that already happened. Still check the ordering: Platform work merged after the run resolved the binding is not in the recorded commit, did not ride, and genuinely needs its own run. Desired pin authority is `environments.settings.release.yoke_pin` on Platform's `yoke-api-stage` / `yoke-api-prod`; environment branches materialize the pin for builds. Promotion restores that materialization when deploy fails and records the desired pin only after success — verify with `yoke release-pin verify`. **That materialization push is a commit the release itself wrote,** so the bridge reads the correlated promotion attempt's immutable `promotion-receipt-RUN_ID-RUN_ATTEMPT` artifact and records its exact `platform_sha` against its own run (`yoke deployment-runs release-output record <run-id> --project platform --commit SHA --promotion-receipt-file PATH`) right after the pin receipt; carried-work attribution reads that record for any commit no item claimed, which identifies it as recorded release output; unowned commits also ship freely as commits made outside Yoke. A Platform ref captured before a pin bump can still roll the engine backward; re-read the pin branch (or desired pin) after any Yoke release before starting a Platform run. **A release is not published until the hosted host has been built against it.** Each hosted-release stage declares an `input_bindings` map (`consumer_sha` bound from Platform `main`), resolved exactly once when the run starts — via a plain `git ls-remote` against Platform's registered checkout, or that project's authorized repository binding on a host holding no checkout, never a not-yet-served field of the release it is gating — and recorded on the run in `deployment_runs.bound_sources`. Every stage dispatch reads that recorded candidate, so a retry cannot drift. Served-identity QA instead requires the promotion attempt's verified deployed SHA, including no-ops; missing or mismatched promotion identity refuses before QA credit. Generic release-output callers retain their bound-source/output behavior. Before the bridge allocates the annotated tag — the first irreversible act — `runtime/api/tools/require_platform_consumer_compatibility.py` takes that exact `--consumer-sha` and dispatches Platform's existing required `platform-release-pin-check.yml` with `product_ref` set to the exact release commit, which redirects that check's build onto the candidate source instead of the pinned wheel, and adopts its conclusion — refusing when proof is missing, failed, or names no revision it proved. It then hands promotion the consumer revision it read, so promotion refuses to ship against a different one. Platform's promotion-time check stays the final backstop. The same pair is advised earlier by the independent `consumer-compatibility-advisory.yml` workflow on pull requests, merge groups, main pushes, and manual dispatches: `runtime/api/tools/consumer_compatibility_advisory.py` uses the same one changed-path scope and, having no durable driver authority of its own, dispatches onto Platform's trunk branch by name and trusts the run's own report rather than demanding an exact match; when the change touches the host-consumed surface it reports checked / not applicable / not checked. Its own run, logs, warnings, and job summary record advisory evidence. Required QA adopts only `yoke-ci.yml`'s conclusion, so advisory failure, cancellation, and timeout cannot turn required QA into an error or block landing. Job-level continue-on-error inside a reusable call cannot provide this isolation when the job times out. The scoped credential is bound to the single advisory step, and the job runs only in `upyoke/yoke`; forks and other copies skip this upstream hosted check. An upstream PR without the credential says the pair was not checked. Why: [`docs/archive/decisions/consumer-compatibility-before-contract-delivery.md`](archive/decisions/consumer-compatibility-before-contract-delivery.md).
- **Control-plane connection authority.** HTTPS `prod` is the normal product/API authority: registered `yoke` commands relay there; it has no local database to open for raw SQL writes. `prod-db-admin` is the paired local-Postgres connection to the same universe — direct database authority for sanctioned source-dev/admin work and audited break-glass SQL; the operator query recipe appears under **Direct database authority for source development and operators** above. Deploy, rehearse, and release command-shaped surfaces also require that admin connection here, because every Yoke release replaces the very API serving this control plane — that is this repo's own shape, not what an ordinary project does, and those projects deploy over their configured HTTPS connection. Neither Yoke nor Platform deploys from a branch push; the private Platform deploy runbook is the detailed operator reference for this installation's cross-repository release train.
- **A release here is two concurrent runs on one lineage.** Stage and production start minutes apart and overlap for most of both runs. Stage drives on the HTTPS control-plane connection; production drives on the paired `prod-db-admin` connection. Both share one commit that has its own `yoke-ci.yml` run: create the CI-gated production run without `--source-ref` so it binds the newest such commit on `main`, then pass that run's `release_lineage` as the stage run's `--source-ref` (stage refuses a missing lineage). Drive them together. That concurrency is correct here because this installation declares stage exists only to test the live control plane, and stage membership owes stage-targeted proof rather than production promotion. Both runs record on prod: stage item QA observes the deployed stage target; production remains final delivery authority, and done requires both obligations. An item owing stage QA rides the stage run even though the production half already holds it — production custody covers only the production target — and its stage proof closes against production because both runs pinned the same commit; a stage run on any other commit skips an item a production run holds, naming that commit, since proof there could never credit. An item without a stage obligation stays off the stage run; when no item owes one, the stage run carries no member and its item-scoped QA stage passes with the named `item_qa_no_member_owes_target` result. Composition refuses a memberless item-QA run (`item_qa_run_without_members`) only when its flow is the completion flow for delivery-ready items no other release holds by landing custody — the production run, never the stage run — and dispatch and later stages re-ask it, failing closed. Activate the stage QA successor only after its engine revision is installed; the prior memberless definition remains disabled history. In a project where stage is a real pre-production gate carrying members, driving production alongside it would promote before stage verified anything.
- **Stage identity for item QA.** The registered stage origin is `https://app.stage.upyoke.com`; its `qa.identity_path` is `/api/orgs/upyoke-stage-1/v1/health`. Configure these through `yoke projects environment update --project yoke --environment stage --url https://app.stage.upyoke.com` and `yoke projects environment-settings merge --project yoke --environment stage --set qa.identity_path=/api/orgs/upyoke-stage-1/v1/health` on prod. The endpoint must report the deployed candidate before stage item QA starts.
- **Fleet migration preflight — one path, each model's declared fleet.** Run `yoke watch preflight -- --project <project> [--model <model>] <environment> [db ...] [--record-receipt ...]` (`--help` for the complete usage). The fleet each model declares in the project's `migration_fleet` capability decides what it rehearses ([`docs/public/reference/db-reference/migration-model-fleet.md`](public/reference/db-reference/migration-model-fleet.md)): Yoke's own model declares `engine_tenants`, so for `--project yoke` it converges a throwaway copy of every tenant database on a connected cluster through the real boot sequence, reads the live databases and nothing more, streams through the sentinel-aware unbuffered watcher, and exits with the preflight's status. The fleet is narrower than every Yoke-schema database on the cluster — the Platform catalog, abandoned scratch databases, and the validation database rehearsal applies history into and leaves behind are each owned by something other than a tenant — so the run rosters every candidate before copying any of them, naming member or not and why; read that roster rather than assuming the fleet. A `named_databases` model (Platform's `registry`) converges the databases it names through its own declared boot command, run from that project's checkout registered on this machine. The positional is the project's registered environment; the paired admin connection is that environment's `release.admin_connection` setting, not a name suffix. `--engine-wheel` is optional. `--record-receipt` writes the receipt the release gates read for the project environment whose fleet the positional named (one environment's receipt never satisfies another; `--receipt-env` names the control plane that records it, not the fleet; the receipt states whether it rehearsed the source tree or a wheel). The receipt is durable state, not telemetry: it lands on that environment's own `environments.settings` document under `release.fleet_rehearsal.<model>`, one leaf per covered history entry and one per covered schema-shape digest, each naming the rehearsal run whose identity sits beside them — so coverage cannot expire, coverage read for one environment can only ever have been written for that environment, and one model's coverage never stands in for a sibling model's. A receipt claims the model's whole declared fleet, so a run narrowed to named databases cannot record one. The release dispatch rehearses exactly the release commit's code: a named-database fleet from a disposable checkout of that commit, the engine fleet only after proving the dispatching engine identical to it. A receipt is stale for an environment when that environment's document does not record something the release commit carries — a history entry name or the schema-shape digest — never merely because the shape moved: a data-only entry rewrites rows without moving the shape at all, and it is the entry rehearsal exists for. Every project's release dispatch runs the rehearsal itself when it finds either uncovered, so the two gates decide on the same axis. Both release gates read it through the registered `projects.environment_settings.get` projection, which authorizes on the project read, so a deploy identity that lacks that permission is told it cannot check rather than told the build is unrehearsed. Why each rule exists: [`docs/archive/decisions/workflow-definitions-are-universe-data.md`](archive/decisions/workflow-definitions-are-universe-data.md) (canonical-serializer drift caused a fleet-wide boot refusal), [`docs/archive/decisions/fleet-preflight-release-gate.md`](archive/decisions/fleet-preflight-release-gate.md) (why the release gate stops the release instead of the fleet), [`docs/archive/decisions/ordered-cumulative-migrations.md`](archive/decisions/ordered-cumulative-migrations.md) (the stage-fleet outage both gaps caused together).
- **Substrate names — read the packet, don't restate.** The `harness_id` enum, the function-call dispatch entrypoint, and the request/response models are rendered by the `main_agent` (and `*_agent`) packets at session start; read them there. Regenerate via `agents.render.run`; check drift via `agents.render.check`.
- **Same-PR packet teaching on Yoke-surface gap failures.** When an agent in a Yoke `/yoke` work item hits a `no such column`, `cannot import name`, or `unexpected keyword argument` failure against a Yoke-owned surface (any `runtime.api.*`, `runtime.harness.*`, or a Yoke DB table / column / Python helper), the SAME PR that observes the failure ships the matching packet teaching: name the real surface in the relevant `schema_api_context_tables_*.py` entry AND add a `notes` clause that names the wrong guess the agent made. The seed catches the gap; the packet rendering surfaces the canonical name to the next agent.
- **Layer-explicit packet names.** Every LLM-facing packet role uses an `*_agent` suffix: `main_agent` (top-level session) plus the five Bash-capable subagents `architect_agent`/`engineer_agent`/`tester_agent`/`simulator_agent`/`boss_agent`. The substrate manifest contract (hooks, identity, cwd binding, render format, supported commands, parity limits) is documented separately as `harness_contract` in [`docs/harness-bootstrap.md`](harness-bootstrap.md) + [`runtime/harness/manifest-schema.md`](../runtime/harness/manifest-schema.md) — deliberately NOT a `schema_api_context` role.
- **Tier-discipline doctrine.** The seven teaching tiers and their backstop HCs (`HC-tier-schema-bleed`, `-tier-cli-shape-bleed`, `-packet-tier-completeness`, `-progressive-disclosure-direction`, `-tier-module-path-resolution`) are documented at [`docs/archive/decisions/teaching-tier-discipline-audit.md`](archive/decisions/teaching-tier-discipline-audit.md).
- **Subagent DB context:** Bash-capable agent prompts (architect/engineer/tester/simulator/boss) carry generated `<!-- YOKE:DB-PACKET role=<role>_agent topic=T … -->` marker pairs the renderer fills with role/topic-scoped schema/API content from `schema_api_context`; the top-level session gets the compact `core`+`claims` spine via `main_agent_packet`. Subagents inherit the packet through the rendered prompt — never hand-copy a stale schema cheat sheet. **The packet is the authoritative schema surface** — consult it (or `information_schema` via `yoke db read` / a direct Read of the schema module) before answering any schema question; don't infer columns/tables from work item or skill prose. Regenerate after schema changes via `agents.render.run`; detect drift via `agents.render.check`. Canonical claim-holder lookup: `python3 -m yoke_core.hooks.sessions_cli who-claims <item-id>` — in-tree, not importable from an installed Yoke; add `--current-episode` to bound the output to the current episode, tagging each claim `episode_scope=current_episode|inherited_from_prior_episode|unknown` plus an `episode_boundary=<ts|none>` line (the portable, episode-blind read is `yoke claims work holder-get PREFIX-N`). Typed work-claim targets use `target_kind` plus one canonical JSON object in the `scope` column (`item={"item_id":N}`, `epic_task={"epic_id":N,"task_num":N}`, `process={"process_key":K,"conflict_group":G}`, `steering={"project_id":N}`), each validated against exactly its own keys; there is no specialized target column, and the packet's `work_claims` stanza carries the live kind list. The drift gate refuses known-stale owner/claim/session guesses.
- **Bash-capable ⇒ packet-capable.** Granting Bash to an agent requires a `*_agent` packet role in `seed.ROLE_TOPICS` + marker pairs in its prompt. Product Manager and Product Designer stay non-Bash by design (tools: `Read, Grep, Glob`; orchestrators pass them context via dispatch prompts) — if they ever gain Bash, they gain packet roles in the same slice. Canonical bodies may carry harness-conditional blocks `<!-- YOKE:HARNESS <id> … -->`; the renderer (`agents_render_conditional`) keeps the matching harness id and elides the rest (known ids `claude`/`codex` from one constant; nested/orphan/unknown surface via `HC-harness-substrate-drift`). Use these to fence primitives a harness does not declare (`Monitor`, `Bash(run_in_background)`, `ScheduleWakeup`, `TaskOutput`, `TaskStop`, `PreToolUse`) so the wrong-harness adapter never inherits them — check `agent_wake` in the target manifest rather than assuming a wake primitive is Claude-only.
- **Workspace-anchored writers.** Repo-tree writers (renderers/generators landing tracked files under `runtime/` or `docs/`) MUST take an explicit `target_root: Path` kwarg; resolving the target from ambient cwd (`git rev-parse`, `Path.cwd()`, bare relative consts) in the hot path is forbidden. Only the CLI resolves `target_root` (`--target-root`/`$YOKE_RENDER_TARGET_ROOT`, else repo-root helper when no anchor and not in a worktree). Primary guard: `workspace_authority.assert_target_under_session_work_authority(target)` — reads the session's live `work_claims`, refuses targets outside the claimed worktree/allowlist (replaced the stale `$YOKE_BOUND_WORKSPACE` snapshot). Tracked-source writers call it before writing; `HC-workspace-anchored-writer-authority` enforces against the canonical `IN_SCOPE_WRITERS` list (`.yoke/doctor/check_workspace_anchored_writer_authority.py`) — add new writers there. Untracked generated-view writers (e.g. `rebuild_board.rebuild_one`, which renders project-local `.yoke/BOARD.md` on explicit request) are out of scope (refusing them would break `yoke board rebuild`) but still call `assert_seed_source_under_target_root(...)` to catch a seed/schema module loaded from a different checkout than `target_root`. Legacy cwd check: lint `lint_workspace_cwd_match.py`.
- **Session identity resolution:** ambient session id resolves automatically — `$YOKE_SESSION_ID` first, then the channels belonging to the harness family this process actually runs under: that family's own session env vars, the hook-written process-anchor registry, and for Cursor the hook-written conversation mapping (`session_ambient_identity`). The owning family is the nearest harness ancestor in the process tree, because every harness session env var is inherited by whatever that harness starts — so a harness launched from inside another harness's shell resolves to its own session, or to nothing when its own channel is out of reach, never to its launcher's. The anchor walk stops at a harness process that hosts many conversations under one pid, on the read side as well as the write side: an anchor above such a host names a *different* session, and resolving through it would act with that session's authority. A harness that neither stamps the env chain nor can be anchored identifies through the conversation mapping instead; never export session env vars to self-bootstrap (`actor_session_missing` inside a harness = infrastructure bug, report it; from a plain terminal the same refusal names the harness-session path instead, and the operations a person runs before any session exists are session-optional by declaration — `terminal_reachable_functions`). Actor id = `harness_sessions.actor_id` keyed by `session_id`, and authority follows the person: a session a person opened binds that person, while a session another session LAUNCHED binds the launching actor transitively (the launch's `requester_actor_id`, read at registration through the authenticated launch side channel, outranks both the machine's OS login and a relay's bearer token; an unreadable launch refuses registration rather than falling back to either). Every action one session takes on another — message, wake, keep-alive, terminate, launch — writes a `SessionActionPerformed` row into the TARGET session's history carrying the ACTING actor (`yoke events query --session <target> --event-name SessionActionPerformed`), and is role-checked against the target's project by `session_action_authority`: project membership to message, wake, hold alive, or terminate a launched worker; project owner or org admin to terminate another actor's interactive session, with refusals naming the actor, the roles it holds, and the action (`docs/archive/decisions/session-actor-follows-the-person.md`). No `get_active_session_id` exists — pass `{"session_id": ...}` alone; dispatcher fills actor_id server-side; `--session-id` = operator-debug override. Scripts importing `runtime.*` live in-tree (`runtime/api/tools/<name>.py`), never `/tmp`; or `pip install -e .` once (`lint_python_runtime_import_in_tmp.py`). Core shell compatibility tools use `yoke_core.domain.json_helper` for JSON and `yoke_core.domain.yaml_helper` for YAML. Client packages (`yoke_contracts`, `yoke_cli`, `yoke_harness`) must not import core helpers; use their existing standard-library JSON parsing. The package boundary is enforced by `tests/import_graph/test_skeletons_importable.py`.
- **Worktree-dev (editing Yoke itself):** the installed `yoke` and bare `python3 -m ...` resolve main's editable install, never a claimed lane. Before merge, run direct lane-source commands through `yoke dev run -- <command>`; it derives every source root from the claimed checkout, runs there regardless of caller cwd on its declared locked .venv, validates the lock/environment without syncing, reports Python/environment identity and all Yoke package and `runtime` import origins, and refuses partial or outside-tree resolution. A nested `yoke <subcommand>` binds too: dev run executes the CLI on the interpreter whose origins it just reported rather than handing the command to the installed launcher, which would resolve its own checkout — so pre-merge `yoke dev run -- yoke watch qa-case -- --requirement-id N` verifies lane code. Inside a post-deploy Command case, run `yoke watch pytest -- <test paths>` directly: the QA runner supplies candidate cwd and the watcher binds it to source. Candidate-bound commands export `YOKE_QA_CANDIDATE_TREE` (JSON root and head_sha), and source wrappers refuse switching to a different root. Candidate-bound Yoke cases bind bare `python3` and `yoke` to candidate packages using the shared source resolver and a temporary Python CLI launcher. The runner records import origins before and after execution; missing or outside-candidate origins record a `QA-CANDIDATE-IMPORT-ORIGIN` refusal instead of a pass. Lane, external-project, and endpoint-only `--allow-tree-mismatch` cases retain product imports. The `watch_pytest`/`run_tests` wrappers already self-bind through the same `yoke_core.tools._source_pythonpath` resolver. Yoke control-plane authority is Postgres; use registered `yoke <subcommand>` surfaces for state access, and treat the retired `worktree paths db` mode as a refusal guard rather than a connection recipe. To look at a lane's UI — or to give a pre-merge Browser case a target that can prove which commit it serves — run `yoke dev run -- python3 -m runtime.api.tools.serve_workbench_for_review`: it starts a second server from the claimed checkout on a port it picks and prints, leaves the machine's own `yoke ui` daemon serving the installed build untouched, and publishes that checkout's commit at `/served-build`, which is what `yoke qa case run --expected-branch/--expected-sha` asks the target for. Commit first: an uncommitted tree publishes `<sha>-dirty` and fails that match closed. To review the workbench a self-hosted server serves itself, browser sign-in included, run `yoke dev run -- env YOKE_ENV=render-proof python3 -m runtime.api.tools.serve_self_host_workbench_for_review`: it serves the claimed checkout as a Yoke server on a port it picks, with sign-in pointed at an in-process provider that approves without a login screen, and prints the sign-in URL that lands a browser on the workbench as the review universe's operator actor.

- **Render-proof setup:** select the registered disposable local connection before setup: `yoke dev run -- env YOKE_ENV=render-proof python3 -m runtime.api.tools.serve_workbench_for_review --prepare-only`. This runs the API boot convergence (additive schema plus permanent migration history) before seeding; starting the same tool without `--prepare-only` converges again before serving. Never initialize a render universe with the relaxed unit-test fixture DDL or a copied schema-init sequence. Remote and prod-flagged connections refuse before database access; convergence failure prevents the review server from starting. Existing universes keep their data and the history retains its restore-point requirements.
