# Installer campaign maintenance

Internal: for maintainers of the Yoke source repository.

## Keep the installer campaign current

`qa.plan_cases.sync` is the registered source-proven sync operation for saved
cases. It replaces future case definitions and preserves materialized requirements,
runs, reviews, and artifacts. Source edits alone do not update an installed plan.
The installer template is generated by `installer_campaign_cases_for_target`;
export it after merge from a clean Yoke source checkout using the plan's own registered
`execution_target`, rather than supplying endpoints or an environment by hand:

```text
yoke qa plan get installer-campaign --project P --full --json > /tmp/installer-plan.json
yoke dev run -- python3 -m yoke_core.tools.installer_campaign_plan --plan-file /tmp/installer-plan.json --cases-file /tmp/installer-cases.json --primary-machine FIRST --joining-machine SECOND
yoke qa plan-cases sync --project P --plan-id {plan_id} --cases-file /tmp/installer-cases.json --json
yoke qa plan get installer-campaign --project P --full --json > /tmp/installer-plan-after.json
yoke dev run -- python3 -m yoke_core.tools.installer_campaign_plan --plan-file /tmp/installer-plan-after.json --check
```

Read `PLAN_ID` from the first receipt, review the exported differences before
replacing cases, then require `matches_source=true` and an empty difference list
from the fresh receipt. The checker compares every authored case field, including
nested method configuration, while excluding storage ids and historical proof.
`--check` exits nonzero on drift and names the install recovery. Run this check
after every installer-template change; install once from the final source when
several changes are being coordinated. The source exporter performs no DB writes;
the registered replacement records the installation in the function-call ledger.
The exporter fetches the repository's default branch from the remote recorded
as tracking it, including when several remotes are configured, and requires
the exact source commit to be its ancestor before writing `--cases-file`; its
receipt names `source_revision`. Uncommitted source, an unmerged lane commit, or an
unreadable upstream refuses as `qa_plan_source_unmerged_or_unverified` and teaches
“sync after merge.” A lane may run `--check` to compare without publishing cases.
Use item-scoped or run-bound correction cases for lane proof; never copy lane
definitions into the shared saved plan through the raw replacement adapter.
The export document carries `source_revision` alongside `cases`; replacement
automatically records it, and frozen releases retain it. A release uses its frozen source cases,
and refuses `qa_plan_source_candidate_mismatch` before materialization or refresh
if the selected source revision is not an ancestor of its candidate. Resync from
the candidate or an ancestor, or release the newer source; never test newer
installer expectations against an older candidate. A source-bound plan cannot
be edited or replaced without source provenance. Older serving builds refuse
source-proven sync as `qa_plan_source_binding_unavailable` before any write.
Existing execution snapshots keep their original definitions and evidence; any
`requirements_behind_plan` returned by replacement need their named refresh path
before reuse, rather than being rewritten as part of the installation.

Choose two distinct registered names from `yoke test-machine list --project P`.
The saved case configurations retain those fixture choices; later source checks
reuse them. The second-machine case must use a different physical host, not a
reset of the first one. A deployment member stage runs the separate host rosters:

```text
yoke watch qa-plan -- --deployment-run-id RUN --stage STAGE --member ITEM --project P
```

Omit a single-host pin for that scope. Standalone executions retain one host
lease; use a one-host saved plan for focused iteration, not a claimed full
multi-host pass. Preserve the baseline and every unperformed case as evidence.

The six recovery cases cover a published predecessor reinstall, local-to-hosted
with and without a backup, a distinct joining machine, explicit uninstall and
late harness discovery. Preparation failures preserve their named reason and
recovery. The late-harness fixture uses a disposable `CODEX_HOME`, preserving
the executable outside discovery and restoring it even when setup fails.
It reruns public machine-only setup after the harness becomes available and
checks native execution and unattended permissions. Codex hooks live in a
project's `.codex/hooks.json`, not the disposable `CODEX_HOME`; project hook
trust and real-session pickup belong to the exploration mission. Personal Codex
home and sign-in files stay in place. Configuration checks do not replace the
exploration's real received-context proof.

Hosted recovery journeys repeat their prepared marker after the installer
exits successfully, then emit a ready marker that the final capture waits for.
The backup journey also repeats its nonempty-backup assertion after exit;
preparation, installer or backup failures never emit readiness. This keeps
the assertion visible after the installer's full-screen display clears.

## Complete machine approval links

```text
Open: https://example.invalid/connect?user_code=AB12-CD34
One-time code: AB12-CD34
```

The gate binds the complete link to the displayed code and the execution
target's declared HTTPS origin. Only one matching user_code is accepted;
unknown parameters, other origins, credentials and fragments refuse as
machine_browser_approval_context_invalid with recovery. Self-hosted
machine/code links preserve the exact wizard-opened path. Coordinate validation
does not grant approval authority; keep the selected human/fixture boundary.

With the dedicated-machine approval exception, the visible native browser
helper (Safari on macOS, the desktop Chromium on a Linux test machine; one
shared matcher in `yoke_harness.machine_browser_approval`) also accepts the
declared origin's `/orgs/<org>/machine-approval/<code>` redirect from `/connect`.
The code must match the displayed one-time code exactly. The redirect may carry
one canonical `selection=all` or a comma-separated list of unique positive
project IDs. Unknown, repeated, empty or encoded query parameters, extra path
segments, fragments and other origins refuse.
The helper presses the visible approval control only in an exact validated
tab, then observes same-origin navigation or the visible "Machine connected"
confirmation in that same tab. An unchanged page without that confirmation
is not approval evidence. Full hosted setup still requires the
run-bound case verdict and independent inspection review.

On Linux the gate first starts the fixture desktop and its Chromium with a
loopback DevTools port and runs the installer's tmux session on that desktop,
so the wizard's link opens in the browser the operator signed in to. The step
always attaches a desktop screenshot. A host without a desktop refuses
`headless_linux_browser_approval_unavailable`; the Machine QA Pack's
[Linux browser approval gates](../../packs/machine-qa/versions/1.3.25/files/docs/packs/machine-qa/linux-host-provisioning.md#browser-approval-gates)
list every refusal and its recovery.

## Local universe birth

State checks inherit directly from the journey that creates their subject:
`token-perms` follows the hosted cold-start Apply, and `universe-born` follows
the local Apply handoff. Token existence, secrets-directory mode 700 and each
token's mode 600 are separate checks with named output; they never print token
contents. A pending browser authorization or pre-Apply Review is not a token
creation prerequisite.

The Review inspection selects "Show all changes" and captures the actual
pending-write names, including reuse of the token already saved by browser
approval, then backs out without Apply. A new token write is not expected on
this path. The regression test compares that line with the installer's own
friendly-line formatter. Category counts alone do
not satisfy that inspection. Saved and frozen cases need the registered
source sync and exact-owner refresh before execution; prior failed captures
remain evidence, and another campaign still requires its own admission.

The local Apply journey chooses Start fresh, waits for `What's your name?`,
and submits a validated first-admin name before `Connect GitHub?`. Command-based
local journeys supply `--admin-name`. Every local journey keeps its Apply report,
successful exit and installer parent-handoff checks.

## Isolated welcome frame

The welcome probe uses an unwritable home to keep the real host untouched.
It proves the authored welcome, automatic uv attempt and diagnosed install
refusal with recovery; exit 1 is expected only with that exact refusal text.
A download failure, missing recovery or successful write does not pass this
probe. Full installation success belongs to the cold-start cases.

## Install the live-session exploration mission

After merge, create the exploration plan for the same declared target as the campaign:

```text
yoke qa plan create installer-exploration --project P --environment SITE/NAME
yoke qa plan get installer-exploration --project P --full --json > /tmp/exploration-plan.json
yoke dev run -- python3 -m yoke_core.tools.installer_campaign_plan --plan-file /tmp/exploration-plan.json --cases-file /tmp/exploration-cases.json
yoke qa plan-cases sync --project P --plan-id {plan_id} --cases-file /tmp/exploration-cases.json
```

Read `plan_id` from the plan receipt. The exporter reads the latest immutable
Machine QA Pack example, so there is one mission source. Check a fresh plan
receipt with the same source checker before running it:

```text
yoke watch qa-plan -- --plan installer-exploration --project P
```

The mission chooses its route through real Claude, Codex and Cursor sessions,
permission modes and representative project archetypes. It requires received
context evidence and meaningful first work reaching its real done state.
The human opens interactive sessions and handles personal approvals. A missing
mode, readiness check, context receipt or terminal outcome remains unproven;
it never passes because configuration files exist. Preserve failed evidence
and add each new failure to the scripted campaign before rerunning after
related installer, setup, connection or onboarding changes.

## Focused install readiness

```text
yoke doctor run --install --project P
```

The saved campaign adds eight isolated refusal cases using the installed
candidate: absent CLI auth, stale dashboard, unobserved session hook, foreign
project binding, unknown guidance, missing instruction pointer, unregistered
machine and stale hook resident. Each requires a named failure and recovery.
These injected cases preserve personal sign-in and host configuration; the
exploration mission separately proves real readiness and received context.
Refresh the saved plan from this source as above, then rerun the campaign after
the candidate is released. Keep unperformed live cases marked unproven.

## Issue-sync opt-in proof

The host adapter expands braces in `entry_surface` as placeholders, including
inside quoted scripts. Use `dict()` for empty mappings in embedded Python.

The scripted `issue-sync-default` case creates an isolated local project and
proves that enabling without verified App access refuses and leaves sync off.
When the existing campaign owner admits this candidate for execution, the
installer exploration must also use
its approved disposable repository to prove these installed paths:

- Complete terminal setup with active App binding; observe no issue-sync
  question, disabled mode and no filed issues.
- In agent-led project setup, observe the relevant explanation and separate
  opt-in offer; declining keeps sync off. Machine-only and no-GitHub setup
  make no offer.
- Deliberately enable with missing Issues write permission; retain the refusal
  and recovery. Grant access, rebind and enable explicitly through each project
  update entry point. A public repository also needs its explicit override.
- Sync one item; retain its short creation notice and returned issue link.
  Repeating sync updates the saved issue. Preserve existing matching behavior.

Keep these obligations with the current campaign/exploration owners and saved
execution. Source sync prepares future definitions; it never starts a fresh run
or grants execution authority. Preserve existing approval and readiness holds;
credit this candidate only through its own legitimately admitted execution.
Retain missing fixture or approval as unproven.
