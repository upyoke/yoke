# Verification, test execution, and command output

The rules file every session loads carries the short normative form of each rule. This document is the deep home the rules file points at: the same rules with the reasoning, the worked failure modes, the flag matrices, and the edge cases that decide close calls. Read the section you need before the action it governs — nothing here is optional background, it is simply longer than a startup channel can carry.

## Testing

- **No hardcoded drifting IDs in tests.** Tests must never contain literal `PREFIX-N`-style work item IDs that drift over time. Use variables, dynamically generated values, or pattern matchers instead.
- **One canonical verification execution — the QA case run IS the final full gate.** Test output capture + streaming is governed by `## Command Output — Hard Rule` above, identically for merges, deploys, syncs, QA, renders, installs, and builds. While implementing, iterate freely and often with the cheap layers: the single failing test, the changed module's paths, and `yoke watch pytest --impacted main --bounded` (impacted selection over the branch diff, owned by `yoke_core.tools.impacted_tests`) — that is the recommended iteration loop and nothing here discourages it, and for a project declaring `ci_workflow_file` that loop runs on CI by default, so iterating costs the workstation nothing (`--local` is only a small targeted check expected to finish in about one minute for the entire invocation — one file or a small test count does not prove a fast runtime; uncommitted work does not justify a slow local run. If a local check exceeds that, interrupt it cleanly, keep the capture as incomplete, commit, and run the selection on CI; do not repeat or background the slow local selection). `--impacted` is bounded by default: when a change touches something reachability cannot bound (a conftest, shared fixtures, the test tooling, or any non-Python file), it reports `selection unbounded (<rule>) — deferring full coverage to the final QA gate` and runs the subset it could still compute. `--bounded` is a no-op. An unbounded verdict mid-iteration means *keep testing what you judge relevant* — the final QA case run covers the rest. Use `--widen` for the local full sweep (CI-outage fallback only). Either way the run prints a greppable `impacted-selection scope=… rule=… triggers=… tests=…` telemetry line into its captures, naming which changed files forced a widening. When the work is ready, the **full** run happens exactly once, through the item's attached Command case: `yoke qa case run --requirement-id <id>`. That single execution produces both the green and the recorded verdict. **Never run a project's full sweep by hand and then re-execute the same tree through QA.** The gate re-runs the identical registered command, so the hand-run buys nothing while doubling compute and shared admission-queue pressure for every concurrent session — one observed session paid 8m16s / 21,371 tests twice on one tree. The case runner streams the command live to stderr and names its raw capture file before the command starts, so an agent is not blind during that one big run; on completion it restates `verdict=… exit_code=… capture=…` on stderr and leaves stdout machine-readable. Re-running a case after **the tree changes** — a fix, a new commit, the post-rebase merge-time run — is a different execution and stays required; only same-tree full duplication is banned. **The gate runs where the project's suite already runs.** A project declaring a `ci_workflow_file` capability gets its registered `quick`/`full` scopes bound to the `command-ci` method (`ci_run` runner): the case run pushes the item's lane branch, dispatches that workflow against it with a correlation id, waits for the run, and records the conclusion as the verdict with the run URL and head sha as evidence — so **commit before running the gate**, since item branches otherwise stay local until merge. **A gate whose watcher was killed did not lose its CI run.** Before it rebases anything, the gate asks GitHub about the exact commit the lane is on: a run that already concluded there is adopted as the verdict, one still in flight is rejoined, and only an unexamined commit is rebased and dispatched — matching is exact-sha, and `ci_run_source` on the outcome line and the recorded row says which happened. The lookup leads the rebase because it is re-entry that needs it: rebasing first moves an unchanged candidate onto an advanced base, which force-cancels the run still answering for it and buys the same verdict a second time. The merge boundary's own post-rebase CI run reuses the same lookup, so a candidate the gate just verified is not verified again. **A turn that ends on a CI run is woken with the verdict.** Every CI dispatch — the gate and `yoke watch pytest`'s remote selection alike — records the run against the dispatching session, and once the turn watching it has ended the control-plane sweep pushes one message carrying the verdict, the run URL, the commit, and the command that resumes the wait (a session still mid-turn is left alone, because it is reading the run itself). So a silent watcher is answered rather than guessed at: read the verdict when it arrives, or grep the raw capture for `interrupted by signal 15` and re-run `yoke qa case run`, which costs one lookup, not another suite. **A quiet watcher is not a dead one.** The gate outlives a single tool-call budget, so a harness that moves the call to a background task or hands back a continuation handle has not interrupted it — the child is still polling. Continue that invocation through the continuation surface your harness declares and re-run only once the process is really gone; the runner says which case you are in on its own progress stream. Taught exception for an overlong *local* test check only: interrupt that test process cleanly once it has exceeded about one minute, retain the capture as incomplete, commit, and continue on CI. Do not interrupt a CI-routed watcher or background the slow local selection to keep waiting. A project also declaring `merge_queue` verifies pull-request-first: the gate rebases the lane onto the base branch, opens the landing pull request, and records that pull request's own entry run as the verdict — one suite instead of a dispatch plus an entry run on the same tree — and the landing then enqueues the pull request the gate opened. Two items gate concurrently because both route to CI; the admission slot is a local-machine resource and never serializes CI runs. Deployed-environment scopes (`e2e`, `smoke`) stay local — they assert against a running site behind a base URL CI cannot reach — and a project with no declared workflow, or any offline operation, keeps the local `command` method (`worktree_run`); that is an explicit plan-case choice, never a silent runtime downgrade, and an unreachable CI case fails with a named reason instead of quietly running the suite on the machine the routing exists to keep free. **Every local full-suite execution takes the machine-wide admission slot:** `yoke watch pytest` and the generic runner both arbitrate for it, so a QA gate and a hand-run watcher sweep cannot execute at once on one machine, while a bare `python3 -m pytest <dirs>` takes nothing and stays invisible to the runs that queue politely — `lint-raw-pytest-full-suite` denies that whole-surface shape outside the wrapper and advises on any other directory sweep (suppression `# lint:no-raw-pytest-check` is audit-only). A queued gate names who holds the slot and how many runs are behind it.

## Visual evidence

- **A rendered capture must name the universe that produced it.** Screenshots are the vetting currency for a UI change, and a reviewer cannot see a capture's data source in the image: the page renders, the layout is right, the rows are real items, and nothing says which control plane answered. Only a diff that happens to add a field the deployed build lacks shows the difference at all, so a pure-CSS or pure-layout change produces captures indistinguishable from correct ones. Render against a database you control by naming its env on the command that serves the view — `YOKE_ENV=<local-env> yoke ui up`, with `yoke env list` naming this machine's connections and `yoke ui down` stopping it. Three things then hold together: the daemon pins that env into the serving process, the view server refuses any connection whose reads it would answer from elsewhere (naming the env to switch to), and the page footer carries the env name into the frame a screenshot captures. So the capture reports its own provenance and a reviewer reads it rather than trusting it. Seed the universe you named through that same env, and the rows you seeded are the rows in the picture. Drive the capture in that order too: the view admits the first request by `?token=`, so take one `snapshot screenshot` against the tokened URL to establish the session, then drive `exec step` against bare paths on the same daemon and profile. Put a `delay` step before the screenshot — the board fetches its rows after the shell mounts, so a capture taken the moment navigation completes photographs `Loading...`. A navigation that lands on an authentication refusal fails the step by name rather than photographing the refusal, and each view names its session cookie after its own port, so a disposable render view and the machine daemon serve at once without logging each other out.

## Command output

- **Capture-first: any non-trivial command MUST be captured to a temp file.** Never pipe a live command invocation directly to `tail`, `head`, or any other truncating consumer — this silently discards failure context and forces a re-run. Applies to anything whose output matters on failure (roughly >5s): tests, merges, deploys, syncs, browser QA, renders, installs, builds, long git ops. Skip only the obviously instant (`ls`, `echo`, `git rev-parse`). The pattern:
  ```bash
  _tmp=$(mktemp /tmp/yoke-cmd.XXXXXX)
  <command> >"$_tmp" 2>&1; _rc=$?
  tail -80 "$_tmp"                           # inspect captured output
  grep -E "FAIL|ERROR|error" "$_tmp" || true # extract failures
  exit "$_rc"
  ```
  Anti-patterns to avoid: `<command> | tail -N`, `<command> 2>&1 | head`, any pipe-to-truncator on a live invocation (the pipe-to-truncator lint denies these for the long-command set — the truncator discards failure context AND masks the exit code). For test suites specifically, run a failing test in isolation rather than re-running the full suite.
- **Capture-first is for long/external commands only — Yoke's own adapters run bare.** The capture-first rule applies to long or external commands (tests, builds, deploys, merges, git) where losing a failed run is expensive. It does NOT apply to Yoke's own registry-covered commands (`yoke <subcommand>`, `db_router`, `service_client`): those are short — run them **bare**, let them print directly (add `--json` for structured output), never wrapped in redirection, pipes, `tail`/`head`, or `| python -c` soup. Wrapping an adapter in capture choreography is denied by `lint-shell-quoted-function-payload` (the agent surface is migrating to clean `yoke <subcommand>` calls — the soup is the old pattern). Long Yoke-ish runs (renders, merges) use the watcher wrappers below, which capture internally.
- **Stream long commands via the harness surface.** Capture-first is the floor and never optional; streaming is required wherever the harness supports it. In Claude, run anything likely >60s via `Bash(run_in_background)` + `Monitor` on the capture, preferring the watcher wrappers (`watch_pytest` / `watch_merge` / `watch_deploy` / `watch_preflight` / `watch_doctor` / `watch_qa_case`) over hand-authored progress filters — the full Claude template + subagent rules live in your Claude harness session rules. Doctor has exactly one shape on every machine, `yoke watch doctor -- (--quick | --full | --only <slugs>)`, which wraps the transport-keyed `yoke doctor run` and streams a verdict line per check whichever transport serves it; `python3 -m yoke_core.engines.doctor` is the source-dev entrypoint, and it refuses before running a check on a relayed control plane. Codex has no idle-wake primitive (`agent_wake.idle_wake = none` in its manifest); a long `exec_command` that outlives its yield returns a `session_id` that must be continued with `write_stdin` until it completes. **A command that outlives its yield is still running — continue it, never relaunch it.** Every supported harness has some way of handing a long command back before it finishes (Claude moves the call to a background task, Codex returns a continuation `session_id`, Cursor notifies on output), and none of those is an interruption: the child process, and anything it is waiting on, is still alive. Read your harness's continuation surface and re-run only once the process is verifiably gone — a relaunch alongside a live first invocation spends the shared resource twice and can cancel the work the first one was about to finish. Taught exception: interrupt an overlong *local* test check (about one minute) cleanly, keep the capture as incomplete, commit, and continue on CI; do not interrupt a CI-routed watcher or background the slow local selection.
- **Don't manually poll a running long command** — the streaming surface is the progress signal. The long-command-polling lint blocks same-capture polling loops (including `sleep N && tail` with N<60s). Subagents must run long commands foreground in one tool call (the subagent-background lint denies background/`Monitor` in subagent context). Suppression `# lint:no-polling-check` unblocks only legitimate post-capture inspections; the Monitor-duplicate/background-waiter tokens are audit-only.

## Verification failure ownership

- **Current-item verification failures belong to the current item.** A future/planned item, planned path claim, or cleanup work item owning a touched file is not a waiver. If the current branch has a failing registered command, gate, or regression, fix it here — unless there's a live active-session conflict or explicit operator waiver.
- **Use dependency and claim reconciliation before override.** If the fix touches a file outside the current claim, use the sanctioned surfaces first: widen the claim, add/verify the serial dependency, wait for or release a live holder, or reconcile the future claim. Do not use `path-claim-override` for a planned future claim when reconciliation works — override is last resort for irreducible live collisions and needs explicit operator approval.
- **Verification summaries are evidence-bound.** A failing registered command can't be reported green by pointing at a future work item. Record the failure, the dependency/claim action, and the rerun evidence that made the item green.

## Health checks

- **Every check declares what it applies to; the runner derives the rest.** A check states its `project_scope` (`any` / `self` / `external`), whether it reads the target project's source tree, which deployment runtimes (`local` / `server` / `hosted`) it runs under, and which project capabilities it needs. The runner resolves the live context — target project, runtime, machine-local checkout, declared capabilities — and derives the applicable set from those declarations. That derived set **is** the per-project default; there is no separate roster to maintain. Never branch on the literal project slug: the self project is whichever mapped checkout *is* the Yoke source tree, so a renamed self project still resolves, and a run's default project comes from the checkout the caller is standing in (`default_project_for_directory`).
- **Passed, failed, and not-applicable are three different answers.** A check outside the applicable set is reported `N/A` with its reason in the report's `## Not Applicable` section and the `na_count` field — never counted as a pass, never dropped silently. A source-tree scan on a runner with no checkout finds nothing; reporting that as `PASS` is a lie the model exists to prevent.
- **Project-local checks live in the project.** A project's own checks go in `.yoke/doctor/`, discovered pytest-style (`check_*.py` files, `hc_*` functions, or an explicit `PROJECT_HEALTH_CHECKS` list) by a runner that holds the checkout, with the same declarations and reporting as engine checks. They import under the `yoke_project_checks` package namespace, so a check can share helpers with a sibling. A module that fails to import is a FAIL, not a skip. Yoke's own source-dev checks live there, not in the engine: the engine roster holds only what is true of every project. Hosted and custom checks are data-driven assertions over the control plane, never arbitrary code in the engine.
