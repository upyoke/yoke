# Database authority and governed mutation

The rules file every session loads carries the short normative form of each rule. This document is the deep home the rules file points at: the same rules with the reasoning, the worked failure modes, the flag matrices, and the edge cases that decide close calls. Read the section you need before the action it governs — nothing here is optional background, it is simply longer than a startup channel can carry.

## Governed DB mutation

Per-project governed contract for data-transforming (and destructive) schema changes and bulk-data changes against a declared authoritative DB. Pure-additive net-new tables/columns are out of scope — they self-propagate on the next boot via the additive-schema converge step (below). Applies to any project declaring a `migration_model` capability (absence = opted out). Every work item carries a **DB claim**; the default `{"state":"none"}` means "no governed mutation declared." A standing invariant found wrong after apply is retired by name and reason in the fleet re-prover, never by editing the ledger-recorded migration module.

- **The DB claim is one concept written through one workflow.** Storage splits across two JSON columns on `items` — `db_mutation_profile` (what the mutation is) and `db_compatibility_attestation` (the safety argument) — but every write path (`/yoke idea` classification, `/yoke refine` repair, `/yoke advance`/`polish` discovery, mid-implementation correction) calls the `db_claim.amend` function id. Skill prose, recovery messages, and docs teach the function id and amendment workflow exclusively; full payload + atomicity contract in `.yoke/docs/reference/db-reference/items-and-epics.md` ("DB Claim — the unified amendment workflow"). Audit history only: `events list --event-name DbClaimAmended` (the gate-consulted reviewed-negative attestation lives on the profile JSON itself).
- **The governed runner is for data-transforming changes, not net-new additive schema.** Pure-additive net-new tables/columns are authored in the schema module and self-propagate to every born universe on the boot after a deploy — the boot-time converge step applies the full idempotent schema (tables + indexes + additive columns) on every boot, so no governed migration and no manual catch-up is needed. **Data-transforming changes (drops, backfills, rewrites) and bulk data on a declared authoritative DB go only through a governed path:** an entry in the ordered migration history, applied by the boot converge, or the explicit audit-fingerprint exception helper. Ad hoc write SQL against any declared authoritative DB is banned. **Authority to converge or apply belongs to the connection, not the command:** on a prod-flagged connection every path into converge or apply refuses, whichever command reached it, because the process is not the build that serves that database — a workstation once carried an ordinary command's authority all the way into a production apply. A process that genuinely serves or owns the database it changes (the server's boot and birth; a restored-archive validator; the fleet preflight on its throwaway copies) declares that with `yoke_contracts.schema_authority.serving_build_authority()` at the call site. Local and self-hosted universes converge their own database untouched. Read-only SQL is always permitted.
- **Every exception path is named.** New audit-fingerprint exception call sites require a paired decision record under `docs/archive/decisions/<helper-name>.md` with the justification. Populate `exception_reason` on the audit row.
- **Applying is the boot converge's job, not a lifecycle phase's.** A server brings its own database up to the code it is running before it serves: the converge computes `history - ledger`, takes an exclusive per-database advisory lock, and applies each pending entry in order, committing the entry and its ledger row in ONE transaction. Boot is fail-hard — a container never serves behind its own schema. No work item applies anything, and no deployment flow carries an apply stage. **A destructive entry also declares the oldest build that may serve against it.** Membership-by-name makes rollback possible and also makes a rolled-back container dangerous: its history lacks the newer entry entirely, so it reports `migrations_current` true while reading columns that are gone. An entry removing a surface sets `MINIMUM_SERVING_VERSION`; omitting it fails at module load, and the applier refuses an entry whose floor is newer than the build running it. **A new entry declares `"next-release"`, never a literal version** — every version an author can name today was cut before the entry they are writing, so a literal on an entry no release carries names precisely the build that cannot serve the schema it produces; module load rejects one, and the sentinel resolves at apply time to the artifact doing the applying, which by construction carries the entry. **The floor is copied into the `applied_migrations` row at apply time** — the reader who needs it is a build too old to ship the entry module, and the ledger row is the only surface they share. `/v1/health` answers `can_serve_this_database` from two independent sources, and **the probe leads because a floor is only ever as right as its author**: it reads the live catalog and refuses when any table or column the running build reads is absent, whatever floor is declared. Ledger evidence then fails closed on top of that: an unknown applied entry without a recorded floor, a known literal floor missing from or disagreeing with its row, an unreadable ledger, an unreadable catalog, or an unresolved build facing an unknown entry refuses service. A known additive entry may legitimately have no floor, and an unresolved source checkout may serve entries its own history contains. Container and deployment gates reject explicit `migrations_current=false` or `can_serve_this_database=false`; cross-version deployment probes accept absent fields from builds that predate that payload contract. **This floor is schema-only.** A new function id declares `minimum_serving_version` on the registry, and a client read of a server-composed response field tolerates absence; neither is a migration, and neither is covered here. Depth: `code-and-cli.md`.
- **What a work item owes is authorship and rehearsal.** Add the entry to the history, then run `yoke migration rehearse PREFIX-N` from a local-Postgres or matching db-admin connection. The command runs against the model's validation surface and records the receipt the evidence gate reads; it refuses HTTPS product connections because project-local code is not relayed. The direct authority owns durable lease and audit receipts and may be prod-flagged; migration code runs only on the separately bound validation database, whose live cluster and database identity must differ from the authority. Rehearsal takes the `LIVE_DB_MIGRATION:<model>` coordination claim and HOLDS it, so a second work item cannot enter migration territory while one is in flight; a failing rehearsal releases it. That claim is a sticky work-claim kind no sweep reclaims, and it is workflow serialization — a different lock from the applier's per-database advisory lock, which is execution serialization. **Never apply a destructive migration without a named restore point** — the applier refuses otherwise. A local or self-hosted install dumps to `YOKE_MIGRATION_BACKUP_ROOT` (defaulting under the machine's Yoke state dir); a hosted fleet sets `YOKE_MIGRATION_RESTORE_POINT` to the managed cluster's point-in-time window. Either way the `migration_audit` receipt records which restore point covers the apply, so recovery is a lookup rather than a reconstruction. **A migration that rewrites rows under a digest or immutability guarantee MUST serialize with the same canonical serializer its readers use**, or it manufactures drift indistinguishable from corruption — a fleet-wide boot refusal is the observed failure. **An entry that transforms rows must be idempotent against its own output already existing, not merely against having already run** — while it sits unapplied the running code can publish the very row it would produce, so applying it later recreates an existing row and trips that table's uniqueness; where its output already exists the entry folds (carry every reference onto the survivor, remove the duplicate) instead of rewriting. **Rehearsal against the validation surface proves nothing about the universes that need the entry**, because that surface is current and a current database has nothing pending: before releasing a build carrying an unapplied entry, run the project's fleet migration preflight — converge a throwaway copy of every live database through the real boot sequence, read those databases and nothing more, and fail on any error. Each project binds its own preflight adapter; `yoke migration rehearse` plus that binding is the portable shape. **The release train enforces this rather than trusting it:** a passing run records a durable receipt — on the rehearsed environment's own settings document, never on telemetry that can expire out from under a covered build — covering exactly the environment whose fleet was rehearsed, and the release refuses before allocating its tag when the build carries a history entry no receipt covers for that environment — one environment's receipt never satisfies another — so where the rehearsal physically runs stays an operator choice while forgetting it stops the release instead of the fleet.

### DB surface doctrine
- **Implementation code and tests validate against the model's declared validation surface.** The env var name is given by `model.runner.connection_env_var`; for Yoke-project's `governed_migration_module` runner the default is `YOKE_DB`. Non-Yoke projects declare their own env var (e.g. `DATABASE_URL`).
- **`/yoke` control-plane commands always use `CANONICAL_YOKE_DB`.** The Yoke control plane is Yoke's; it is not forked per worktree or per declared model. **Client-side code reaches control-plane rows by relaying, never by connecting:** a control plane reached over https has no local database to open, so `db_backend.connect()` and the no-DSN `connect_psycopg()` refuse the call there with `RemoteControlPlaneConnectionError` — deliberately outside the `Exception` hierarchy, because one instance of this defect was a bare connection inside a blanket `except` that silently skipped its write. Use `control_plane_transport.local_connection_or_none(...)` + `relay(...)`; code that genuinely means to open a local database it holds authority over declares it with `yoke_contracts.control_plane_locality.local_authority_exempt()` at the call site — the named exception, never a path allowlist. The client CLI sets the mark for one invocation (an explicitly pinned DSN opts out); server-side dispatch never sets it. `HC-ambient-authority-connection-guard` keeps the factory unbypassable by refusing an undeclared `psycopg.connect(db_backend.resolve_pg_dsn())`.

### Project posture: `projects.breakage_policy`
Every project carries one operator-authored stance on how aggressively schema and data cutovers can land in a single slice:

| Value                     | Meaning                                                                      |
|---                        |---                                                                            |
| `founder_cutover`         | Default. Hard cutovers are first-class; expand-contract requires justification. |
| `compatibility_required`  | Old + new readers may coexist. Hard cutover requires justification.            |

Breakage policy is stored per project rather than inferred from its slug. Projects default to `founder_cutover`, and an operator may explicitly select `compatibility_required`.

### `db_mutation_profile.migration_strategy` and the gate matrix
`compatibility_class` is a SAFETY classification (does the diff preserve readers/writers across the merge boundary?). `migration_strategy` is the AUTHOR'S DECLARATION about the operational shape:

| Strategy            | Meaning                                                                  |
|---                  |---                                                                       |
| `additive_only`     | Net-new tables/columns/data that do not replace an existing live surface. |
| `hard_cutover`      | Old surface is replaced/deleted in the same slice.                       |
| `expand_contract`   | Old and new surfaces coexist temporarily.                                |

The two axes pair through the joint gate and the governed-runner rehearse/apply gates into the matrix:

| `breakage_policy`        | `migration_strategy`  | Result                                                     |
|---                       |---                    |---                                                         |
| any                      | `additive_only`       | Allow regardless of `compatibility_class`.                 |
| `founder_cutover`        | `hard_cutover`        | Allow when class is `pre_merge_safe` or `pre_merge_breaking`. |
| `founder_cutover`        | `expand_contract`     | Block unless `migration_strategy_justification` is non-empty. |
| `compatibility_required` | `hard_cutover`        | Block unless `migration_strategy_justification` is non-empty. |
| `compatibility_required` | `expand_contract`     | Allow regardless of `compatibility_class`.                 |

Block messages name BOTH axes so the operator knows which side to amend. Note: pure net-new additive schema needs NO governed migration — it self-propagates on boot via `converge_core_schema`; the `additive_only` strategy here covers additive changes deliberately authored as a governed migration (e.g. bundled with a data backfill, or a project with no boot-converge path).

### Compatibility class doctrine
- **`compatibility_class` and `migration_strategy` are orthogonal — never substitute one for the other.** A `pre_merge_safe + hard_cutover` is a clean drop-and-replace that happens to keep readers happy; `pre_merge_breaking + hard_cutover` is the founder-cutover slice that intentionally breaks compat in one step.
- **`pre_merge_safe` claims are attested** by a frozen `db_compatibility_attestation` with the authored fields (`pre_merge_readers_writers`, `invariants`, `rehearsal_commands`, `residual_risk_notes`) present and non-empty.
- **Silent class relaxation is forbidden.** Tightening (`pre_merge_safe → pre_merge_breaking`) is recorded as a `class_escalations` entry on the attestation. Scanner-detected banned patterns always tighten.

### Joint-gate dependency awareness
The cross-item overlap detector honors `item_dependencies`: when a candidate item and a non-terminal other are linked by a blocks/depends-on edge, overlapping `rebuild`, data-kind, and schema-only declarations on shared surfaces no longer block the candidate's transition (operator-authored ordering already enforces non-simultaneous live application). Disjoint-table and disjoint-column cases are unaffected.

### Stranded-lease recovery
- **Human-only operator release.** `yoke coordination-claim release --project P --key LIVE_DB_MIGRATION:<model_name> --reason "..."` emits a WARN `OperatorLeaseRelease` event before the release mutation lands. It refuses to run from a hook context and records the operator reason permanently on the claim row. Sticky claim kinds have no automatic reclaim, so this is the only early release.

## Worktree DB authority

- **Yoke control-plane DB authority is Postgres, never a constructed file path.** From any checkout or linked worktree, use registered `yoke <subcommand>` commands or the function-call surface for reads/writes; everyday raw diagnostic SELECTs use `yoke db read "SELECT ..."`. When a mutation has no registered command, reach the paired local-Postgres `*-db-admin` connection (pass `--env NAME`) and use the operator-debug query path named by `yoke db` `--help`: that path is direct SQL write authority for source-dev/admin and audited operator-debug recovery, and it is not the agent-default. It exists only where the operator already runs the control plane on this machine (a local or self-hosted install, or Yoke source-dev); a project relaying to a control plane someone else operates has no such connection, so escalate the missing command rather than seeking control-plane database credentials. Discover configured connections and what each unlocks with `yoke env list`. Never infer authority by appending a legacy DB filename to `$PWD`, `CLAUDE_PROJECT_DIR`, or a worktree path.
- **A linked worktree is not a Yoke control plane.** Paths under `.worktrees/<branch>/` are code execution surfaces. Do not read or write worktree-local legacy DB files; control-plane reads and writes go through the connected Postgres authority.
- **Worktree-local DBs are validation surfaces only when explicitly surfaced.** If a migration model provisions a validation DB, use the emitted Postgres env bindings. Do not substitute that DB for `/yoke` control-plane reads, item queries, events, or project metadata.
- **Environment settings are projected, never dumped.** Read only explicit scalar leaves with `yoke projects environment-settings get --project <slug> --environment <name> --path <key.path>`; the registered read refuses root or container projections, and merge receipts return changed paths rather than the settings document. Never inventory `environments.settings` as a whole.
